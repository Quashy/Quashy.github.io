项目背景

业务背景

某大型制造企业安全生产管理平台（安全隐患治理模块）已完成某阶段需求编写。当前代码已实现：

  • 安全隐患项目信息发起（/api/v1/cases/add）
  • 分页查询（/api/v1/cases/page）
  • 详情查看、编辑、删除

缺失核心能力：审批流。项目提交后无法流转到各级安全员审核、无法退回、无法指派。

需求来源

公开需求摘要定义了：

  • 6 种业务流程（按发起人身份区分）
  • 7 个状态阶段
  • 多级审批路由（一线单元 → 业务部门 → 企业，最多三级）
  • 退回/直退机制（退回后重新提交直接回到被退回节点）
  • 指派/确认机制（上级指派给指定治理单元安全员）
  • 或签机制（多人处理任一处理即可）
  • 亮点项目审核（多级评星，本期不实现）
草稿→ 审批中→ 审核退回→ 治理中→ 验收中→ 验收退回→ 已验收

新表：审批记录表

CREATE TABLE IF NOT EXISTS public.approval_event
(
    id               VARCHAR(64) PRIMARY KEY DEFAULT gen_random_uuid(),
    case_id       VARCHAR(64) NOT NULL,
    node_type        INTEGER NOT NULL,   -- 1=审批 2=确认指派 3=验收 4=亮点审核
    node_level       INTEGER NOT NULL,   -- 1=一线单元 2=业务部门 3=企业
    handler_id       VARCHAR(64),
    handler_name     VARCHAR(64),
    action           INTEGER NOT NULL,   -- 1=通过 2=退回 3=需上级协助 4=指派 5=确认
    reason           TEXT,                  -- 退回原因
    action_id        VARCHAR(64) NOT NULL, -- actionId，重试幂等键
    rejecting_node   VARCHAR(64),          -- rejectingNode，原拒绝节点
    target_node      VARCHAR(64),          -- targetNode，退回目标节点
    comment          TEXT,                  -- 审批意见
    action_time      TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_approval_project
    ON public.approval_event (case_id);
CREATE INDEX IF NOT EXISTS idx_approval_handler
    ON public.approval_event (handler_id);
CREATE UNIQUE INDEX IF NOT EXISTS uq_approval_action
    ON public.approval_event (case_id, action_id);
设计要点
  • 只 INSERT 不 UPDATE——完整审计轨迹，无并发冲突
  • 退回事件同时记录 rejectingNode 与 targetNode，重提直达原拒绝节点
  • actionId 唯一约束抵御客户端重试，事件日志仍保持只 INSERT 不 UPDATE
  • node_type 区分审批/确认/验收/亮点——一个表覆盖全流程
  • 索引覆盖 case_id（查项目轨迹）和 handler_id（查我的审批）

核心逻辑链路

POST /api/v1/cases (提交): 判定身份 → flow_type → status=1, current_level=路由首节点
  → revision=revision+1（实例 CAS）→ INSERT approval_event(actionId) → createTasks()

POST /api/v1/cases/approve: 校验 current_handler → need_upper_help?
  → YES: 任务条件 CAS + revision CAS，通过后 INSERT event(actionId, action=需上级协助)
  → NO:  指定治理负责人, INSERT event(actionId, action=通过), 流转到治理阶段

POST /api/v1/cases/reject: 校验 current_handler → 列出 returnableNodes
  → INSERT event(actionId, rejectingNode=当前节点, targetNode=X, action=退回, reason=...)
  → status=2, current_handler=退回节点处理人, invalidateTasks()

resubmit: 目标节点修改后查最近退回事件 → status=1, current_level=rejectingNode
  → 修改后直达原拒绝节点, createTasks()

设计决策逐条记录

以下 13 条决策覆盖了审批流设计中的全部关键技术选择，每条包含背景、方案对比、Trade-Off 分析和最终决策。

DECISION 1 状态字段设计

背景：需求定义了 7 个阶段，其中"审批中"内部分三层（一线单元→业务部门→企业），退回后需"直退"回被退回节点而非从头流转。

问题：用单一 status 扁平枚举，还是用 status + current_level 组合？退回目标存主表还是从审批记录推导？

方案 A: 扁平枚举

单一 status 字段，枚举 15+ 个值。

优点缺点
一字段，前端直接映射状态值膨胀到 15+
无需组合逻辑查询"所有审批中"要 WHERE status IN (1,2,3)
直观同 phase 不同 level 切换就是改 status，与 current_level 冗余
方案 B: 复合字段 (status + current_level)

status=1(审批中) + current_level=2 → 业务部门审核中

优点缺点
查询"所有审批中" WHERE status=1退回时 current_level 语义变化
与现有表结构兼容前端需组合两个字段展示文案
亮点审核多级可复用
✅ 方案 C: 复合字段 + 事件记录退回节点（最终选择）

在方案 B 基础上不向主表写退回目标，退回事件同时记录 rejecting_node（rejectingNode）和 target_node（targetNode）；重提时按最近一条退回事件直达原拒绝节点。

优点缺点
单一数据源——退回目标只在审批记录里详情页需 JOIN 审批记录取退回目标
不存在双写不一致列表展示 status=2 + current_handler 已够用
语义清晰：主表管状态，审批记录管历史
▼ 最终决策
方案 C
  1. 列表展示不需要"退回目标级别"，status=2 + current_handler=处理人 A 已够用户理解
  2. 详情/处理页本来就要查审批记录，退回目标可以一并获取
  3. 避免主表和审批记录之间数据不一致的风险
  4. 退回关系作为事件事实保存，避免主表状态和历史目标双写不一致
DECISION 2 审批记录存储方式

背景：老系统用 JSON 字段 approval_history 存主表，存在查询困难、并发覆写等问题。

问题：继续用 JSON 字段还是拆独立审批记录表？

方案 A: JSON 字段 (延续旧系统)
优点缺点
不建新表，DDL 成本低查询需全表扫描 JSON
读详情一次查询统计需求不可做
团队熟悉并发覆写风险高、代码拼 JSON 易出错
✅ 方案 B: 独立审批记录表（最终选择）
优点缺点
查询灵活，全走索引多一张表
支持并发——各自 INSERT 不互斥详情多一次 DB 查询（非瓶颈）
扩展性好、统计友好

记录粒度：

  • 粗粒度：每次操作 UPDATE 或新增。一个项目 3-7 条。
  • 细粒度（最终选择）：只 INSERT 不 UPDATE。一个项目 5-15 条。
▼ 最终决策
方案 B + 细粒度 INSERT-only
  1. JSON 方案在"退回后重新提交"场景有致命问题——要查找最近 action=reject 元素，JSON 操作极易出错
  2. INSERT-only 无并发更新冲突
  3. 完整时间线，排查问题方便
  4. rejectingNode/targetNode 存审批事件 → 重提路由从事件事实推导（与决策 1 呼应）
DECISION 3 处理人（安全员）来源

背景：审批流转时需要确定每个节点的处理人。文档说"在组织管理页面配置安全员"，但组织管理页面在外部系统。

问题：从外部系统实时查安全员，还是本地缓存？

方案 A: 实时查 人员标签服务
优点缺点
已验证，旧系统跑通每次流转都调外部接口，强依赖外部可用性
安全员变动实时生效人员标签服务 超时或异常 → 审批流直接报错
开发量最小标签服务稳定性未知
✅ 方案 B: org_role_cache 本地缓存 + 按需播种 + 定时同步（最终选择）
审批流转 → 查 org_role_cache
  ├─ 命中 → 直接使用
  └─ 未命中 → 调 人员标签服务 查 → INSERT org_role_cache → 使用

定时任务（1h）→ 全量刷新 org_role_cache
优点缺点
审批流不依赖外部系统可用性需开发同步逻辑
第一次使用时自动播种安全员变动有延迟（同步周期）
可加手动触发同步接口应急
方案 C: 实时查 人员标签服务 + Redis 短缓存
优点缺点
比 B 开发量小引入 Redis 依赖
缓存失效时仍可能打不可用服务
▼ 最终决策
方案 B

决策逻辑（无需了解 人员标签服务 稳定性）：

人员标签服务 稳定 人员标签服务 不稳定 方案 A 完美 审批流瘫痪 方案 B 稳定可靠 稳定可靠
方案 B 在 人员标签服务 稳定时多付出的代价是常数（一张表 + 一个定时任务），避免的风险是无上限的（审批流瘫痪）。这是一笔天然不对称的 Trade-Off——用可控的工程成本消除不可控的外部风险。
DECISION 4 或签机制实现方式

背景：需求定义"一个节点有多个处理人时，采用或签方式"——任意一人处理即可。

问题：用什么机制来管理"其他人待办自动消除"？

方案 A: 仅靠 current_handler + 业务代码
优点缺点
简单清理逻辑散落在业务代码
方案 B: 独立待办表
优点缺点
可追溯多一张表
✅ 方案 C: current_handler + todo_record（最终选择）

复用已有 todo_record 表：

流转 → current_handler = "A,B,C" → 每人 INSERT todo_record
某人处理 → 自己的 = done; 其他人同节点 = -100(已失效)
优点缺点
复用已有表case_id 需改为 VARCHAR(64)
职责分离：current_handler / todo_record
▼ 最终决策
方案 C

技术方案 QA

面向：团队 Review / Mentor 提问预期 / 后续接手者快速理解。覆盖流程机制、数据设计、架构韧性、扩展性、运维边界共 30 个问答。

核心流程

Q1项目状态是怎么流转的？
status=0(草稿)        current_level=0
    │  提交
    ▼
status=1(审批中)      current_level=1(一线单元)
    │  通过/需上级协助
    ▼
status=1(审批中)      current_level=2(业务部门)
    │  通过/需上级协助
    ▼
status=1(审批中)      current_level=3(企业)
    │  通过 + 指定治理负责人
    ▼
status=3(治理中)      current_level=0     ← 本期截止，后续实现

 退回路径（任意审批节点可触发）：
 status=1(审批中)  →  退回  →  status=2(审核退回)
     事件记录 rejectingNode + targetNode
     targetNode 修改后重新提交 → status=1，current_level=rejectingNode（直达原拒绝节点）
Q2怎么判断项目当前在哪个状态、哪个审批节点？

组合两个字段：status 决定大阶段（审批中/退回/治理中/…），current_level 决定审批中的具体层级（一线单元/业务部门/企业）。流程实例的 revision（API 语义为 version）用于并发 CAS。

-- 所有审批中的项目
SELECT * FROM case_main WHERE status = 1;

-- 所有在业务部门审批中的项目
SELECT * FROM case_main WHERE status = 1 AND current_level = 2;

退回状态时 current_level 无意义，前端展示靠 status=2 + current_handler 即可。

Q3退回后重新提交，怎么实现"直退"？
  1. 审批人点退回 → approval_event INSERT 一条带唯一 actionId 的 action=退回 事件，同时记录 rejectingNode 和 targetNode
  2. 主表 status=2，current_handler 改为退回目标节点的处理人
  3. 退回目标节点修改后重新提交 → 查 approval_event 最近一条退回事件的 rejectingNode → status=1，current_level=rejectingNode
  4. 直接回到原拒绝节点，跳过中间层级；重复提交由 actionId 唯一约束幂等处理
退回目标只存在审批事件里，主表不存；rejectingNode 记录拒绝发生处，targetNode 记录退回修改节点，修改后重提直达原拒绝节点，避免双写不一致。
Q4怎么确定每个节点的处理人是谁？

核心原则：审批流不依赖外部系统实时可用性。org_role_cache 表是本地缓存层，人员标签服务 只做播种和定时刷新。

审批流转需要处理人
      │
      ▼
查 org_role_cache 表（leader_level + org_id）
      │
  ┌───┴───┐
  │ 查到？  │
  ├───┬───┤
  │YES│NO │
  │   │   ▼
  │   │ 人员标签服务查安全员
  │   │   ├─ 查到 → INSERT org_role_cache（播种）→ 使用
  │   │   └─ 未查到 → 报错"该组织未配置安全员"
  │   │
  ▼   ▼
返回处理人列表 → 生成待办

定时任务（1h）：人员标签服务 → 全量刷新 org_role_cache

审批机制

Q5或签机制具体是怎么工作的？
流转到节点 → current_handler = "处理人 A,处理人 B,处理人 C"
           → 每人 INSERT 一条 todo_record（status=0）

处理人 A处理   → 自己的待办 → done
           → 处理人 B、处理人 D同节点待办 → 批量 UPDATE status=-100（已失效）
           → current_handler → 下一节点处理人

处理人 B回来   → 待办已 -100，不可见

任意一人处理即可，同节点其他人的待办自动消除。todo_record 复用已有表。

Q6"需上级协助"和"通过"在行为上有什么区别？
通过需上级协助
审批意见同意同意
流转方向指定治理负责人 → 治理阶段上级审批节点
current_level不变（已到最终节点）+1
出现场景所有审批节点非最高级审批节点

统一用 action=需上级协助 记录在审批记录表。node_type 已有上下文。

Q7审批通过后项目去了哪里？本期做到什么程度？

审批人在最后一级审批点"通过" → 弹窗指定治理负责人 + 完成时限 → 本期截止。后续阶段设计实现 status=3(治理中) 及后续阶段。

Q8退回时用户可以选哪些退回节点？

从 approval_event 查询该项目所有 action IN (通过, 需上级协助) 的历史记录 → 去重 → 就是可退回节点列表。不另建配置表。

示例（业务部门员工上报流程）：

当前节点 = 企业级安全员
历史审批节点 = [一线单元安全员, 业务部门安全员]
可退回节点  = [一线单元安全员, 业务部门安全员, 填报人]  ← 填报人始终可选

上报流程指派流程
发起人选不选治理单位必选治理单位
流转方向发起人 → 本级/上级安全员逐级审批发起人 → 治理单位安全员确认

flow_type1/2/34/5/6

指派流程中，发起人不是审批链的一环——提交后直接到目标单位安全员确认。

Q10发起人身份是怎么判定的？为什么用 mock？

沿用 findCurrentUser() 的配置模式，用 mock 用户配置判断身份。等 org_role_cache 表数据完善 + 定时同步跑通后，查当前用户是否在 org_role_cache 中 + leader_level 是多少 → 判定身份。人员标签服务的稳定性未知，不在登录路径上依赖它。

数据设计

Q11数据库为什么不用 JSON 字段存审批记录？
  • 查询"我审批过的所有项目"要全表扫描 JSON → 走不了索引
  • 统计"本月退回率"几乎不可做
  • 并发场景下整字段覆写 → 数据丢失风险
  • 退回后重新提交时找最近退回记录的 returnToLevel → JSON 操作极易出错
Q12审批记录表为什么只 INSERT 不 UPDATE？
  • 完整审计轨迹：每次操作都是一条新记录，永远不改历史
  • 无并发冲突：多个人审批时各自 INSERT
  • 时间线自然形成：按 action_time 排序就是完整链路
  • 退回后重交不丢历史：新旧审批记录共存，可追溯"第一次通过是谁、第二次通过是谁"

事务与并发

Q13审批操作涉及多表写入，怎么保证一致性？

一次审批操作至少涉及：

UPDATE case_main (status, current_level, current_handler, revision=revision+1)
  WHERE case_id = ? AND revision = ?   -- 流程实例 version/revision CAS
INSERT approval_event (actionId, action=通过)   -- (case_id, actionId) 唯一
UPDATE todo_record (同节点其他人标记 -100)   -- 任务条件 CAS
INSERT todo_record (下一节点处理人 × N)

所有操作在同一事务中。@Transactional(rollbackFor = Exception.class)，任何一步失败全部回滚；事件日志追加写入，主表和任务表用条件更新保护并发。

Q14或签时两个人同时点"通过"怎么办？

双层乐观并发控制：

UPDATE todo_record
SET status = 'done'
WHERE case_id = ? AND node_id = ? AND assignee_id = ? AND status = 0; -- 任务条件 CAS

UPDATE case_main
SET status = ?, current_handler = ?, revision = revision + 1
WHERE case_id = ? AND status = 1 AND revision = ?;

如果处理人 A 先完成，处理人 B 的任务条件或流程实例 revision CAS 影响行数为 0，事务回滚，前端提示"该审批已被他人处理"。

Q15用户连续点两下"通过"，会重复写两条审批记录吗？

不会。服务端先按 (case_id, actionId) 唯一约束去重：重试同一个 actionId 返回第一次结果；随后任务条件 CAS 与流程实例 revision CAS 防止并发迁移。公开 Demo 对应字段名为 operationId。

Q16项目编号并发怎么办？

兜底方案：数据库 case_no 加唯一索引。INSERT 冲突时 Java 层捕获 DuplicateKeyException，重新生成编号重试（最多 3 次）。

CREATE UNIQUE INDEX IF NOT EXISTS idx_case_no
    ON public.case_main (case_no);

容错与边界

Q17如果查不到安全员怎么办？

显式报错，不静默跳过。返回明确错误信息："组织 [XXX] 未配置 [一线单元级] 安全员，请联系管理员"。这比"提交成功但不知道去了哪里"好得多。

Q18通知推送失败了，审批流还走不走？

审批流照走，推送是旁路。

主路径：改 status + 写审批记录 + 更新 current_handler  →  必须成功
旁路：  调 消息中心 推送待办消息 → 失败记日志 + 告警，不阻塞流转
Q19删除项目时审批记录怎么办？

审批记录保留，不级联删除。审批记录是独立审计数据，不因项目删除而消失。如果确实需要清理，DBA 手动操作，代码不做级联删除。

架构与风险

Q20如果 人员标签服务挂了，审批流还能用吗？

能。只要 org_role_cache 表里有数据，审批流转完全不走外部调用。

场景人员标签服务 挂了的影响
审批流转（org_role_cache 命中）无影响
审批流转（org_role_cache 未命中、首次播种）阻塞，显式报错
定时同步任务本次同步跳过，下一周期重试
冷启动时（表全空 + 人员标签服务 挂了）确实会阻塞，建议部署脚本里加一条初始同步，启动时立刻跑一次。
Q21怎么回滚？数据表结构变更了怎么办？

只回滚代码，不回滚数据库。

  • 新字段全部是 ADD COLUMN IF NOT EXISTS + 有 DEFAULT 值 → 老代码忽略这些字段
  • 新表 approval_event 老代码不读写 → 不影响
  • 旧代码状态只用到 status=0/1 → 新状态值不会出现在旧请求里

没有破坏性 DDL（改类型 / 删列），代码回滚到上一个版本即可。

数据生命周期

Q22老数据迁移怎么处理？

现有 case_main 表里可能有 status=0/1 的存量数据，flow_type 是新字段，老数据为 NULL 或默认值 0。

UPDATE case_main
SET flow_type = 1   -- 默认按"员工上报"处理
WHERE flow_type IS NULL OR flow_type = 0;

同时在 page 查询里兼容 flow_type=0（视为不筛选）。

Q23审批时间线按什么顺序展示？

按 action_time ASC 排序。每条记录自带 node_type + node_level + action，INSERT-only 的表本身就是完整链路，不需要额外设计"轮次"或"阶段"字段。

权限边界

Q24安全员能不能看到其他部门安全员审批的项目？

当前 page 查询逻辑：非草稿全部可见。这意味着部门 A 的安全员能看到部门 B 的审批中项目。如果业务上不允许跨部门查看，需在 page 查询新增 initiatorOrgId 过滤。这属于业务需求决策，不在本次技术设计范围内，但需提及避免误解。

上线运维

Q25定时同步任务第一次什么时候跑？

建议部署脚本里加一条初始同步——启动时立刻跑一次，而不是等 1 小时后的定时触发：

启动顺序：
1. 执行数据库升级脚本（建表/加字段）
2. 执行老数据迁移 UPDATE
3. 启动 Spring Boot
4. 立即触发一次 RoleDirectorySyncTask（全量同步 人员标签服务 → org_role_cache）
5. 后续按 cron 表达式周期执行

冷启动时表是空的，提前跑一次避免第一个用户提交审批时触发按需播种的延迟。

扩展性

Q26如果以后增加了"集团级"审批（第 4 级），系统怎么改？
  1. current_level 新增枚举值 4
  2. org_role_cache.leader_level 新增值 4
  3. flow_type 路由链加一级
  4. approval_event.node_level 新增值 4

不涉及表结构变更——所有关键字段都是 INTEGER 枚举，扩展加值即可。

Q27如果某个流程的审批链变了，系统怎么改？

修改 flow_type 对应的路由逻辑（一个方法），不涉及数据迁移。历史项目不受影响——审批记录已完整记录实际走过的节点。

Q28如果安全员数据源从 人员标签服务 换成了其他系统，系统怎么改？

只改 RoleResolverService.resolveHandlers() 里的外部调用实现 + RoleDirectorySyncTask 的同步源。org_role_cache 表作为统一缓存层隔离了外部变化，上层审批流转代码完全无感。

Q29如果状态阶段要增减，怎么改？

status 枚举扩展（如 status=7 新增"集团退回"），不涉及表结构变更。或者复用现有 status=2（审核退回）+ 审批事件 targetNode 区分退回级别。推荐后者。

Q30如果以后要改成会签（所有人都要处理），怎么改？

todo_record 的消除逻辑从"同节点全部标记 -100"改为"仅标记自己的 → done，等所有人都 done → 统一流转"。current_handler 和 approval_event 不需要改。
